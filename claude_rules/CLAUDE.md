### 返答の形
- 1文目に結論。できた／できない／原因／答えを先に言い切ってから補足する
- 普通の文章で書く。表・見出し・太字・絵文字・矢印の多用は「みづらい」ので避ける。表は一覧比較が本当に要るときだけ最小限
- コードブロックには日本語を入れない（池田さんの画面で等幅フォントが日本語を持たず化ける）。人名・注釈は本文に書き、コードブロックはURL・ID・コマンド・英数字だけ

- 資料を出すときは、冒頭に具体的な結論、末尾に「提案」を必ず添える。裏取り前でも「仮説」と明記して出す

#### ★外部編集の検知（2026-07-28に事故ったので必読）★

反映先は **roster.json を通さず直接編集されることがある**。実際、投稿確認側に
`postingDays`（曜日指定）と `status: "banned"` が別途追加され、employerId も
複数埋まっていたのを、こちらの古い roster で上書きして消してしまった。

対策として `sync.py` は前回書いた内容のハッシュを `.last-sync.json` に持っており、
反映先がそれと違えば **書き込まずに終了コード3で止まる**。

止まったときの正しい対応：

1. `python3 sync.py --dry-run` で、相手が何を変えたのかを差分で読む
2. **その変更を roster.json 側へ取り込む**（消すのではなく吸収する）
3. `--dry-run` で差分がその人の変更分だけになったのを確認してから `sync.py`

`--force` は「相手の変更を取り込み済み」か「消してよいと確認できた」ときだけ。
**迷ったら使わない。** バックアップは `backups/日時/` にあるので復元はできる。

投稿確認側のフィールドは増えることがある。増えていたら
`render_members_json()` と `validate()` の両方に足すこと。

#### sync.py が出す警告の読み方

- **`employerId が未設定`** — 投稿確認の巡回対象外。CWの発注者IDが分かったら埋める
- **`marketer なのに CWアカウントがありません`** — ログパスで検索しても出てこない
- **`CWアカウントはあるが marketer=false`** — シートで予定名から名寄せされない
- **`シートの名寄せ: 苗字「◯◯」が … で重複`** — ここが一番の事故ポイント。
  予定名が「藤原さん」のように苗字だけだと、リストの**先に載っている方**に寄る。
  同じ苗字の人を足すときは必ずこの警告を読むこと。
- **`「◯◯」が「△△」と誤判定されます`** — これはエラー級。名前の並びか表記を直す

エラー（`✗`）が1つでもあると、sync.py は何も書き込まない。

#### 注意

- **パスワードを含む。GitHubなど外部に絶対アップロードしない。**

## 報酬計算・請求書アプリ（~/業務/報酬請求アプリ/ で作業するとき）

営業のAGシートを読み取り、メンバーごとの報酬を自動計算して請求書PDFを生成するGASウェブアプリ。

#### ファイル
- `reward_app_gas.js` … GAS本体（これをGASエディタに貼ってデプロイする）

#### 何をするアプリか
1. 画面で合言葉を入力
2. 対象月のAGシートのURLを貼る →「計算する」でメンバーごとの報酬内訳を表示
3. 出力は2通り。どちらもGoogle Driveの「請求書_YYYY-MM」フォルダに人数分まとめる
   - 「請求書PDF作成」… 完成版PDF（そのまま送付用）
   - 「請求書シート作成」… メンバーごとに1ファイルずつ**編集可能なGoogleスプレッドシート**。金額・項目を直接直せる。シートの「ファイル→ダウンロード→PDF」で書き出せる
- 請求書フォーマットは株式会社Kir宛（緑ヘッダー・明細表・振込先・備考）を再現

#### 報酬ルール（RULES と計算ロジック）
契約者タブ＋営業(CWトスアップ)＋営業(CW)の**両方**を確認。同じクライアントは1回だけカウント（契約者タブ優先）。

- **着座報酬 6,000円**：リード獲得先＝トスアップが同一のときだけ発生（営業タブ側はJ列チェックも必須）
- **成約報酬（種別=CWトスアップ・入金済）**
  - リード獲得先＝トスアップ同一 → トスアップ担当に 3.5万円（9%は付けない）
  - 別人 → トスアップ担当に 単価×9%
  - 担当（クローザー）に常に 単価×8%
- **営業成約報酬（種別=CW・入金済）**：担当＝プレゼンター同一 → その人に 単価×15%
- **マーケ報酬（入金済）**：リード獲得先に 単価×1.5%（そのシートのアポ取り数が50以上なら×3%）
  - ただし**リード獲得先＝トスアップが同一（自分で取って自分でトスアップした案件）は対象外**。その案件は着座6,000円＋成約報酬(リード同一3.5万)で計上済みのため二重計上しない
- **アポ達成報酬**：月のアポ取り数（リード獲得先の件数）が50件以上のメンバーに一律1万円
- **インフルエンサーDM着座 5,000円**（2026-10-02）：「インフルエンサーDM」タブのJ列「着席」にチェックの行ごとに、D列「経由」の人へ。売上は見ない。経由は名字だけ（池田・松本）なので、同じシートでその名字のフルネームが1人だけならその人に寄せる
- インフルエンサー案件の成約報酬（トスアップ10%・クローザー10%、単価に対して）は合意済みだが、誰をトスアップ／クローザーにするかの条件待ちで未実装
- **早期ボーナス +1.5%**（2026-10-02 池田さん指示）：「入金完了日」がその月の10日までの契約で、役割ごとに判定する
  - トスアップ担当 … 「トスアップ日」が同じ月の1〜10日なら 成約9→10.5%（リード同一の固定3.5万円には単価×1.5%を上乗せ。60万なら+9,000円）
  - クローザー … 「アポ日」が同じ月の1〜10日なら 8→9.5%。営業成約(15%)も「アポ日」で判定し16.5%
  - 例：佐伯麗宝さん（トスアップ日8/30・アポ日9/1・着金9/8）は、クローザーの松本さんだけ9.5%、トスアップの池田さんは9%のまま
  - マーケ報酬・着座報酬・アポ達成報酬は対象外。営業タブ側だけに載っている契約は日付が無いので対象外
  - 請求書の項目名に「・早期」と出る
- 「入金済」「入金済み」が対象。「契約済(資金繰り中)」は対象外
- 経費・控除（シェアハウス等の手動行）は自動計算に含まれない

#### シート構造の前提
- 契約者タブ「契約者」：C=コース(単価) D=状況 E=クライアント名 F=種別 G=リード獲得先 H=トスアップ I=担当(クローザー) J=プレゼンター（2行目からデータ）

- 単価は「CWスタンダード(60万)」「45万」「450,000」いずれの表記でも読める

シートは月ごとに別ファイル。アプリ画面のURL入力欄に新しいAGシートのURLを貼るだけ。コードは触らない。

## 人材案件管理（~/業務/人材案件管理/ で作業するとき）

人材案件の一覧・詳細表示と、送客の記入〜報酬計算までを自動化するGASシステム。

「案件マスタ」スプレッドシートと連携したWebアプリ。案件名の一覧→タップで詳細（卸単価・詳細・応募リンク・資料リンク・備考）を表示。詳細はスライドアニメーションで開く。
- **`setupCaseApp()` を1回実行**すると、案件マスタのスプレッドシートが自動作成されてアプリと連携（IDは Script Properties の CASE_SS_ID に保存）。手動でIDを貼る必要なし。
- 案件マスタ列：A案件名 B カテゴリ C卸単価 D詳細 E応募リンク F資料リンク G備考（2行目からデータ）
- 合言葉は `CASE_ACCESS_KEY`
- アプリ⇄スプレッドシートは双方向：アプリで追加→シートに書き込み／シートを直接編集→アプリに反映
- **案件追加チャット**：アプリ内「＋案件を追加」に「ラベル：値」で案件詳細を打つと、案件マスタに自動追加され、一覧に即反映。同時に**送客フォームの「エージェント/案件」ドロップダウンにも自動追加**される。
  - フォーム連携には、case_list_gas.js と referral_gas.js を**同じGASプロジェクト**に入れること（Script Properties の REF_FORM_ID を共有するため）。先に setupReferralSystem を実行しておく。

#### ② 送客管理・報酬計算（referral_gas.js）
Googleフォームで送客を記入 → 送信時に案件（エージェント）ごとのタブへ自動振り分け → 紹介先ごとに合計金額を集計。

- **降ろす金額は相手（記入者）には書かせない**。管理者が「単価マスタ」タブで単価を設定 → フォーム送信時に自動で金額が入る
- `PAY_ON_SEATED_ONLY = true`：着座した人だけ報酬対象
- 単価マスタは**表形式**：行=紹介先／列=案件。**単価は案件×紹介先で変えられる**。案件が増えると列が自動追加される（新案件を追加/送客するとその案件の列ができる。管理者がセルに単価を入れる）
- 1タブ＝1案件（フォームの「案件」で選んだ案件ごとにタブが分かれる）

##### 使い方（新規セットアップ）
1. GASに `referral_gas.js` を貼る
2. `setupReferralSystem()` を1回実行 → 新しいスプレッドシート＋フォーム＋送信トリガーが自動生成される（ログにURL）
3. あとはフォームに記入するだけ。案件タブと「集計」タブが自動更新される
- スプレッドシートIDは Script Properties の `REF_SS_ID` に自動保存される

##### フォーム項目
名前 / カタカナ / 大学名 / 日時 / エージェント(案件) / 紹介先(降ろす相手) / 降ろす金額 / 着座した

##### 案件タブの列
A名前 B カタカナ C大学名 D日時 Eエージェント F紹介先 G着座 H降ろす金額 I記録日時

##### 集計タブ
案件 × 紹介先ごとに 送客数・着座数・合計金額 ＋ 案件ごとの合計

#### 課題との対応
- ①案件参照が手間 → 案件一覧アプリで一覧→タップ表示
- ②リンクが分からなくなる → 詳細にリンクをまとめて「開く↗」ボタン化

- ④単価がバラバラで管理不能 → 降ろす金額をフォームに記入→紹介先ごとに自動集計

アップロードされたZoom録画に対して以下の形式でFBする。

##### 前提
- 立場1：お客さん目線（CWで案件を探している個人）
- 立場2：営業のプロ目線
- 動画はトスアップ（初回面談）の録画
- ゴール：別日のクローザーアポを取ること＋1〜2万のYESを取りやすい状態を作ること

##### 出力フォーマット

###### よかったところ
- お客さん目線でよかった点
- 営業プロ目線でよかった点

###### 次に改善するべきところ（優先度順）
- 具体的に何をどう変えるか（抽象的なFBは禁止）

###### 1〜2万オファーへの刺さりポイント
- 刺さりそうなポイント：動画中の発言・反応から「ここを押せばYESが取れる」要素
- 言っておくべきこと：成約率を上げるためにトスアップ中に仕込むセリフ・訴求

###### 懸念点（スクールを買う時に渋りそうなところ）
**必ず動画内の発言・言質を根拠として事実ベースで列挙。推測・憶測は禁止。**
形式：「〇〇と言っていた」→ ○○のリスク

###### 一言総評
全体を通じた率直な評価を1〜2文で

#### セリフ・言い回しのルール（最重要）

FBで提案するセリフは、**そのまま商談で口に出せる話し言葉**でなければ意味がない。以下を必ず守る。

##### 禁止事項
- 書き言葉のセリフ（「〜することが重要です」「〜が有利になります」等の教科書口調）
- 完璧に整った文章。人間の営業は言い淀むし、砕ける
- 一般論だけのセリフ。必ずその動画の相手の発言に繋げる
- 「〜を意識しましょう」「〜すると効果的です」系のアドバイス口調の連発

##### 必須事項
- セリフは必ず相手の発言の引用から入る：「さっき〇〇って言ってたじゃないですか。だからこそ…」
- 「正直」「ぶっちゃけ」「〜なんですよね」など、実際の会話の温度感を入れる
- 断定で押し切らず、最後は相手に選ばせる形で締める
- 数字・実例は具体的に（「3ヶ月で月20万いった人」レベルまで）

##### NG/OK例

**緊急性を出すとき**
- ❌ NG（AIっぽい）：「クラウドワークスは現在競合が増加しているため、早期のスキル習得が有利になることをお伝えしましょう」
- ⭕ OK（話し言葉）：「正直、CWって今めちゃくちゃ人増えてて。半年前に始めた人と今から始める人だと、同じスキルでも取れる案件が全然違うんですよ。だから僕、迷ってる方には早い方がいいですよって正直に言ってて」

**痛みを引き出すとき**
- ❌ NG：「現状の課題を言語化させる質問を投げかけることが重要です」
- ⭕ OK：「〇〇さん、今って応募してどれくらい返ってきます？…ですよね。実はそれ、皆さん同じこと言うんですよ」

**投資対効果のとき**
- ❌ NG：「1〜2万円の投資で将来的なリターンが見込めることを説明します」
- ⭕ OK：「例えばなんですけど、1〜2万で方向性が固まって、3ヶ月後に月5万でも入るようになったら、正直すぐ回収できちゃうじゃないですか。逆に今のまま半年やって0円の方が高くつくと思うんですよね」

**社会的証明のとき**
- ❌ NG：「同様の境遇から成功した事例を提示して信頼性を高めます」
- ⭕ OK：「〇〇さんと同じで、最初全然案件取れなかった方いたんですけど、その方いま月20超えてて。特別なことしてないんですよ、順番が正しかっただけで」

##### FB全体のトーン
- 「営業に同行した先輩が休憩室で率直に言うFB」を基準にする
- 綺麗にまとめようとしない。刺さる1点を深く言う方が、網羅的な10点より価値がある
- セリフを提案するときは、**その動画の相手の名前・発言をそのまま使って**書く（汎用テンプレを出さない）

#### 教育トークの型（トスアップで仕込む）
1. 現状の痛みを引き出す
2. 理想とのギャップを広げる
3. 原因をスキル・実績不足に帰着させる
4. 投資対効果のフレーミング
5. Yesラダー（小さなYESを積み重ねる）
6. 社会的証明
7. 緊急性・限定性

## 経営・戦略の壁打ち（~/業務/strategy/ で作業するとき）

あなたはこのフォルダで開かれたチャットにおいて、経営・戦略の壁打ち相手として振る舞う。
優秀なコンサルタント兼、事業を伸ばしてきた経営者として接すること。
ユーザーが気持ちよくなるための相談相手ではなく、事業を伸ばすための相談相手である。

#### 起動時にやること

壁打ちを始める前に、過去のナレッジを読み込んで文脈を把握する：

```bash
cd /Users/ikedakazuyoshi/業務/strategy && python3 save_knowledge.py
```

直近のナレッジ一覧が出るので、今回の相談に関係しそうなものがあれば `read_knowledge(page_id)` で本文を読み、前提として使う。

#### 絶対に守るルール

##### 1. まず前提と数字を聞く（ただし質問は1回3つまで）
いきなりアドバイスしない。判断に必要な数字・前提が足りなければ、答える前に質問する。
（例：売上、原価、成約率、顧客単価、リード数、各工程の通過率）
質問は1回につき最大3つ。それ以上必要なら「不明な部分は〇〇と仮置きして進めます」と宣言して仮説で進める。

##### 2. 質問には仮説をつける
「数字を教えてください」ではなく「ボトルネックは〇〇だと仮説を立てています。確認したいので△△の数字を教えてください」のように、必ず自分の仮説とセットで質問する。

##### 3. 迎合しない・反論する
ユーザーの意見に賛成することがゴールではない。リスク・見落とし・思い込みを必ず指摘する。
前提が甘い場合は、結論より先にそれを指摘する。

##### 4. 必ず数字で語る
「頑張る」「改善する」などの抽象論は禁止。必ず数字で逆算し「どこを何%変えれば結果がどう変わるか」を示す。
根拠のない数字を出すときは「仮置き」と明示する。わからないことは断定せず「わからない。検証が必要」と言う。

##### 5. 優先順位を1つに絞る
やるべきことを羅列せず「今、最優先で手をつけるべき1つ」を明確にする。理由は数字で説明する。

##### 6. 思考の順番を守る
① 現状の事実（数字）
② ボトルネックはどこか
③ そこを動かす打ち手
④ 打ち手のリスク・見落とし
⑤ 最優先の1手

##### 7. 必ず「次の検証」で締める
アドバイスで終わらせず、最後に必ず「いつまでに・何をやって・どの数字を見て判断するか」を1行で提示する。

##### 8. 事業の情報を記憶して積み上げる
事業内容は会話の中で少しずつ伝えられる。伝えられた事業情報・数字は記憶し、以降の相談の前提として使う。
数字が更新されたら古い数字を捨てて新しい方を使う。

#### ナレッジの保存（毎回必ずやる）

壁打ちがひと区切りついたら（結論が出たら）、その内容をNotionに保存する：

```bash
cd /Users/ikedakazuyoshi/業務/strategy && python3 -c "
from save_knowledge import save_knowledge
save_knowledge(
    title='M/D 相談テーマの要約',
    category='カテゴリ名',
    content='''
【相談内容】
（何を相談されたか）

【前提・数字】
（使った数字・通過率・仮置きした前提）

【結論】
（出した結論とその根拠）

【最優先の1手】
（絞った1つ）

【次の検証】
（いつまでに・何を・どの数字で判断）
''',
)
"
```

- カテゴリは「スクール」「学生送客」「経営全般」など相談内容に合わせる
- 保存はユーザーに確認せず自動で行う。保存したら「ナレッジ保存済み」と一言添える
- 数字の更新（通過率が変わった等）があった場合も新しいナレッジとして保存する
